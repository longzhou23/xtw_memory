# 小天文 Memory：面向群聊的事件记忆形成与状态条件读取

小天文 Memory 研究一个具体问题：**在多人、话题交错的持续对话中，如何把历史消息形成可追溯的记忆，并在当前对话需要时，将有限且有用的历史材料带回工作上下文？**

本仓库是这一方向实际开发中的**可运行研究原型**。目前已实现从消息持久接收、话题组织、临时与长期记忆形成，到基于当前对话的召回、关联传播和适用性判断的核心链路。原始消息、形成结果、来源引用与读取轨迹分别保留，用于检查错误发生在哪个环节。

当前工作重点是从“链路能够执行”推进到“独立实验能否证明记忆有用”。**实现状态、运行验证和效果结论分开报告**，下文列出已有证据与尚未完成的验证。

[使用与复现](docs/USAGE.md) · [研究问题与评测设计](docs/RESEARCH_DESIGN.md) · [有限注意力扩散](docs/ATTENTION_DIFFUSION.md) · [读取协议与验证记录](docs/READ_PATH.md)

## 系统结构

```text
原始消息 → 持久接收队列 → CPU Router → Episode 独立 FIFO
                                             │ 批量挤出
                                             ▼
                                      Temporary Writer
                                             │ Episode 关闭
                                             ▼
                              Final 节点 / 关系 / 来源证据
                                             │
当前对话状态 S → 历史快照 → 本地语义召回 / 图扩展 / 注意力扩散
                                             │
                                        候选及轨迹
                                             │ 显式适用性判断
                                             ▼
                                   字符预算内的工作上下文 C
```

Event（原始事件）进入 Episode（话题容器）；FIFO（先进先出工作上下文）挤出消息时形成 Temporary（临时记忆），话题关闭后整理为 Final（长期记忆）。读取以当前实际可见的对话状态为条件，不使用隐藏题目、标准答案或人工指定的目标记忆。

当前 HTTP 读取入口面向已经形成的长期记忆，不包含全部活跃 Episode 的工作状态。网关提供消息接收与内部上下文读取，**不生成 Bot 回复**，也不包含群聊平台适配器、图片理解或管理界面。

## 核心机制

### 先形成记忆，再判断当前是否需要它

写入采用“非生成式路由 + 生成式整理”的分工：Router 判断新建还是延续话题，Writer（记忆整理模型）处理批量挤出和话题关闭。当前每个 Episode 的 FIFO 容量为 12 条，每次挤出 6 条；来源检查约束引用与结构，未决内容与确定陈述需要区分。

消息已经保存、记忆已经形成、候选已经找回，是三个不同的状态。**被召回不等于应该被使用。** 默认 `autoSignificance=false`，只返回候选与轨迹，不将候选加入工作上下文；显式启用后，对非空候选最多进行一次模型判断，再按预算打包。形成的上下文是内部材料，不是最终回答，也不构成对外披露授权。

### 三种读取方式，共同接受后续判断

本地 BGE 语义模型生成候选并重排，读取线索来自当前可见的说话者与消息。HTTP 入口支持：

| 模式 | 如何生成候选 | 希望比较的问题 |
|---|---|---|
| `formed_multiquery` | 多线索直接召回形成记忆 | 不依靠关系传播能做到什么？ |
| `graph_expansion` | 在关系图中按最佳路径扩展 | 显式关联能否补回遗漏材料？ |
| `attention_diffusion` | 在图上迭代分配有限注意力，再按阈值选取 | 多路累积与竞争是否带来额外收益？ |

有限注意力扩散是**待验证的启发式图方法**，不是已经证明有效的认知机制。三种模式采用共同的重排与候选预算设置，但实际计算成本不相同。公式、参数、关系方向及阈值边界见 [有限注意力扩散](docs/ATTENTION_DIFFUSION.md)；其他实现条件见 [方法与评测设计](docs/RESEARCH_DESIGN.md)。

### 保留可检查的工程边界

接收回执只表示消息已持久保存，不表示整理完成；消息处理完成也不保证已经形成 Final。读取使用同一 `scope`（数据空间）的历史快照，存在未完成写入时拒绝读取，返回前检查版本是否变化。调用顺序是**先用当前状态读取，再按需要写入当前消息**，避免把当前消息混入历史候选。

完整的接收、失败恢复、时间边界与预算规则见 [网关协议](docs/GATEWAY.md) 和 [读取协议](docs/READ_PATH.md)。

## 当前研究问题与下一步

当前最重要的问题不是继续增加记忆机制，而是：**在相同历史和上下文预算下，形成记忆是否比强原文检索更有用，是否值得额外的整理成本？**

研究推进顺序是：先冻结独立评测集，覆盖不需要记忆、多话题交错、跨时间更新与干扰项；再比较强原文检索与形成记忆，联合报告错误、下游效用和形成成本；随后检验图扩展、扩散与适用性判断各自的贡献，并公开失败案例。

完整的研究假设、数据划分、对照组、消融实验与复现要求见 [研究问题与评测设计](docs/RESEARCH_DESIGN.md)。**该文档是待执行方案，不是已经完成的实验。**

当前尚未证明形成记忆优于强原文检索，也未证明注意力扩散优于直接召回或图扩展。Router 错误可能沿写入链路传递，生成式整理可能丢失限定或误解来源，传播与适用性判断也可能引入错误。来源追踪让这些问题可检查，并不自动消除它们。

系统目前面向内部小规模使用，采用完整索引与受限快照；不提供大规模性能或长期真实群聊收益结论。本仓库不是完整训练与评测工程，不包含真实聊天、训练数据或原研究版 benchmark（评测）页面。

## 运行与检查

### 不调用模型的软件测试

Linux、Python 3.11+，从仓库根目录执行：

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install "numpy>=1.24,<3"
cd research-mvp
PYTHONPATH=.:../router_deploy python -m unittest discover -s tests -t . -v
```

测试使用合成输入与模型替身，不需要下载权重或调用外部模型。这是软件行为检查入口，不是实际 Router / Writer 的效果演示。

### 实际写入与读取

按 [使用与复现指南](docs/USAGE.md) 准备依赖、Router 权重与封存配置、本地 BGE 模型以及 Writer 环境，再执行写入与当前状态读取。网关使用本地 SQLite 与回环 HTTP。

Router 权重通过 [GitHub Release](https://github.com/longzhou23/xtw_memory/releases/tag/memory-minimal-20261005-router-v02) 分发。**该 Release 的源码标签早于读取链路加入；获取当前完整实现请使用 `main`，核对历史验证时使用对应提交。** BGE 模型需要另行准备；固定模型身份见 [方法与评测设计](docs/RESEARCH_DESIGN.md#模型身份与复现边界)。

真实 Writer 与适用性判断会向模型服务发送相关消息与来源材料，并产生调用成本；本地语义读取在模型准备完成后可离线运行。项目尚不提供旧数据库兼容与数据迁移，配置或封存身份变化时应使用新数据库并保留旧实验记录。
